Section 1In one minute

A dependency scanner tells you "Pillow has 36 advisories". It cannot tell you whether a single one of them is reachable from the internet in your code. Blast Radius loads your repository into FalkorDB as one graph and lets an AI agent walk it: advisory, to package, to the functions that use it, up the call chain, to the HTTP endpoint an attacker can hit. Then it names the owner, verifies the safe version, bumps the dependency on a branch, opens a real pull request, and writes its decision back into the graph so it remembers next time. Every step is a graph query you can read.

Section 2The problem, in plain words

Modern apps are mostly other people's code: a Python project pulls in 100 to 200 packages. Security databases (OSV, GitHub Advisories) publish thousands of vulnerabilities a year against those packages. Tools like Dependabot or pip-audit compare your lockfile to that list and produce a long table. The table answers "which packages have known bugs". It does not answer the three questions a security engineer actually has:

  1. Is it reachable? Does any code path from an HTTP endpoint ever call the vulnerable function? Most advisories are not reachable in a given app.
  2. From where? Which endpoint, which handler, through which functions? Does it need login? Is it deployed?
  3. Who fixes it, and what is the fix? Who owns that code, which version is safe, and can we open the PR now?

Answering those by hand means grepping, reading call sites, running git blame, checking the changelog. Hours per advisory, times hundreds of advisories. The data is inherently connected: advisories connect to packages, packages to functions, functions to functions, functions to routes, files to authors. That is a graph problem, and that is why FalkorDB is the heart of the product rather than a visualisation on top of it.

Who is it for: security engineers and backend maintainers who receive advisory noise and need a defensible, explainable answer fast; and reviewers who want to see the evidence rather than trust a score.

Section 3What we built (eight capabilities)

1. Code graph builder. Point it at a repo (GitHub URL, subfolder link, zip, local folder). It parses Python (FastAPI, Flask, Django, DRF) and JavaScript/TypeScript (Express, Next.js, NestJS), reads the lockfile, asks OSV for advisories, runs git blame, detects ORM models, and loads everything into one FalkorDB graph. Mealie (78k lines) builds in about 30 seconds: 14,234 nodes and edges.
2. The agent. A Claude model in a tool-use loop. It is told the method (identify, reach, owners, fix, act, record) and may only state facts that came back from tools. It discovers the 21 tools from an MCP server and calls them; the tools run Cypher against FalkorDB.
3. Graph algorithms as tools. Shortest attack paths (algo.SPpaths), choke points (algo.betweenness + algo.pageRank), blast radius (algo.BFS). These are FalkorDB procedures, not Python loops.
4. Actions. Plan the minimum safe version, verify it against OSV, bump it on a git branch (pyproject, requirements, package.json), open a pull request on a fork, and record the decision as a node in the graph.
5. Live-deployment awareness. Connect the running app: OpenAPI, GraphQL, or the compiled frontend bundles (read by the LLM). Endpoints learn whether they are deployed, whether they need login, and what parameters and payloads they take. Deployed, unauthenticated, reachable endpoints rank first.
6. Explainability. Step cards with the exact Cypher, rows and latency; an evidence graph that grows as the agent works and replays the attack path hop by hop; a full-screen story; a self-contained HTML report; clickable endpoint detail cards.
7. Memory. Decisions are written back to FalkorDB. The next run starts with "this was already triaged as FIX_PROPOSED on …" and builds on it. The funnel tile and the advisory feed show it.
8. Multi-repo console. One graph per repository or live site; switch with the picker; scenario buttons are generated from what the graph contains.

The one query to know by heart

MATCH (p:Package {name: $pkg})<-[:USES]-(sink:Function)
MATCH path = (h:Function)-[:CALLS*0..6]->(sink)
WHERE (h)-[:EXPOSES]->()
MATCH (h)-[:EXPOSES]->(e:Entrypoint)
RETURN e.id, length(path) AS hops, [r IN relationships(path) | r.how] AS how, e.live, e.auth_required
ORDER BY hops

Read it aloud: "find functions that use the package; find handlers that reach them in up to six calls; return their routes with hop count and how each call was resolved". In SQL this is a recursive join you would never run interactively; in FalkorDB it returns in tens of milliseconds.

Why a graph, not Postgres or a vector database?

Relational: reachability is a variable-depth recursive join, slow and awkward to write. Vector search: it finds similar text, not what calls what; it cannot prove a path exists. A property graph stores the relationships directly, and a path query is the native operation. The algorithms (shortest paths, betweenness, PageRank, BFS) come for free on the same data.

Section 8FalkorDB: what exactly we use, and what breaks without it

  • Multi-graph: one graph per repository or live site; GRAPH.LIST drives the picker.
  • Variable-length paths (CALLS*0..6) for reachability and transitive dependency chains.
  • Algorithms: algo.SPpaths, algo.betweenness, algo.pageRank, algo.BFS.
  • Indexes: range on every key; full-text on function text and advisory text.
  • GRAPH.RO_QUERY for every read; the agent's ad-hoc tool can only read.
  • Write-back: Decision nodes, live flags, parameters and payload fields as array properties.
  • Batched UNWIND … MERGE loading: 14k elements in seconds.

Remove FalkorDB and there is no reachability, no attack path, no owner, no drift, no memory, no evidence graph: there is no other database in the product. That is the rule-3 test and it passes.

Section 10Live-app discovery, explained

Given a URL, Blast Radius reads only what an anonymous browser would receive, never logs in, never probes:

  1. OpenAPI / Swagger document at the usual paths, following Swagger UI or Redoc pages to the real spec. Gives methods, paths, security, parameters and request-body schemas.
  2. GraphQL introspection, if the server allows it.
  3. Frontend bundles: the page's scripts and one level of scripts they load themselves (Flutter's main.dart.js, Vite/Next chunks, up to 16 MB). A regex pass finds route-like strings; then Claude reads the network-call regions (large bundles split into three parallel chunks) and returns endpoints with method, auth hint, query parameters and body fields, as structured JSON.

Results join the code graph: live=true, auth_required, confirmed=true for calls proven in frontend code versus bare route strings, drift (only in deployment / only in code), and the API areas. The agent ranks live + unauthenticated + reachable first. Publicly callable endpoints are flagged red; unknown-auth calls on file, certificate, export or payment paths amber: in the graph, the live card, the answer and the report. Verified on mealie's public demo (273 documented endpoints, 271 matched to code, 14 only in code) and on a compiled Flutter app with no spec at all (127 calls confirmed from an 8.7 MB bundle in ~45 s).

Section 11Explainability and the UI

  • Phase bar: Identify → Reach → Owners → Fix → Act → Record lights up as the agent works.
  • Step cards (right): one per tool call, in plain English; open one to see the MCP request, the exact Cypher, rows and latency; the fix card shows the diff.
  • Evidence graph (centre): grows with each step; after the run it replays the attack path hop by hop with captions; on frontend-only graphs it tours the API areas instead. Zoom in or hover to read labels; click an endpoint for its detail card (full URL, auth, evidence, parameters, payload, handler, owners, advisories on its paths); double-click to expand neighbours.
  • Answer (left): verdict badge, red "needs attention" lines, endpoints table, attack path, owners, fix, PR link.
  • Funnel tiles and feed: the headline numbers and the newest advisory per package with one-click triage; both update when decisions are recorded.
  • Story mode (full screen, auto-opens after a run): Question → Investigation → Attack path → Verdict, keyboard controlled.
  • HTML report per run: self-contained, with KPIs, steps, Cypher, diff and the evidence graph.

Section 13Honest limits (say these before judges ask)

  • Static analysis. Calls resolved by import or definition are "high" confidence; calls matched only by method name are "medium" and drawn dashed. Dynamic dispatch and reflection can be missed. Runtime traces (OpenTelemetry) would be the next step.
  • Reachable ≠ exploitable. The agent narrows by the advisory's trigger (image decoding, multipart parsing, JWT algorithms), but a human still confirms. That is why NEEDS REVIEW exists and names the owner who should confirm.
  • Frontend-derived endpoints are best effort. Confirmed calls are marked; route strings are kept but labelled unconfirmed. Payload fields come from what is visible in the code.
  • Languages: Python and JavaScript/TypeScript today. Advisories need a lockfile or pinned requirements.
  • Not hosted. It needs an Anthropic key and clones repositories, so it runs locally with one command.

Section 14Questions judges will ask, and short answers

Why FalkorDB and not SQL or a vector store?

Reachability is a variable-depth path question. In a property graph that is one Cypher pattern returning in milliseconds; in SQL it is a recursive join; a vector store finds similar text, not a proven path. And the algorithms run on the same data.

Where is the multi-hop reasoning?

Advisory → package → function → up to six calls → handler → endpoint, plus function → author and function → table. Four to six hops per answer, in one query, then ranked by algorithms.

Where is MCP?

agent/mcp_server.py serves all 21 tools over stdio; the agent lists them at start and calls them by name through agent/mcp_bridge.py. The step cards show the MCP request and response. BLAST_TOOLS=direct bypasses it for comparison.

How do you stop the model inventing endpoints?

The system prompt forbids stating anything not returned by a tool; every claim in the answer is traceable to a step card with its query and rows. Confidence is quoted from the graph (how each call was resolved).

What does the agent actually change?

A git branch with the dependency bump, a pull request on the fork with impact, endpoints, path and owners in the body, and Decision nodes on the graph. Nothing is pushed to the upstream project.

Is the live-app connection safe and allowed?

It reads only public documents and public JavaScript; no login, no credentials, no probing unless the operator explicitly asserts authorization to one tool. Only paths, methods, auth flags and parameter names are stored.

What if the advisory is not reachable?

The agent says NOT REACHABLE or NEEDS REVIEW, states exactly what evidence would flip it, names the owner who should confirm, records the decision, and offers the upgrade as optional hygiene.

How long did ingestion take, and does it scale?

About 30 seconds for 78k lines; batched UNWIND/MERGE; indexes on every key. Django healthchecks (2,710 functions) also works. Larger monorepos would be split by service, one graph each.

What was built with AI assistance?

Disclosed in the README: an AI coding assistant wrote code under direction; the graph model, the verification on real repositories, the demo and the decisions are the participant's, who can explain every query in docs/queries.md.

What would you do next?

Runtime traces to confirm reachability, a GitHub Action mode that triages new advisories on every push, cross-repository impact (one advisory across every graph), and more languages.

Section 17Glossary

Advisory / CVE / GHSAa published report that a package version has a security bug. CVE and GHSA are id schemes; OSV.dev aggregates them.
Lockfilepoetry.lock, uv.lock, package-lock.json…: the exact versions an app installs. Advisories are matched against these versions.
Direct vs transitive dependencydirect: your project asks for it; transitive: pulled in by another package (starlette comes with fastapi).
Endpoint / route / handleran HTTP address the app serves (POST /api/users/{id}/image) and the function that runs when it is called.
Call graphwhich function calls which. Walking it from a handler to a sink is "reachability"; each call is a "hop".
Sinkthe function that actually uses the vulnerable package.
Cypherthe graph query language FalkorDB speaks: MATCH (a)-[:CALLS*1..6]->(b).
Graph algorithmshortest paths, betweenness (how many paths pass through a node), PageRank (importance), BFS (everything reachable). FalkorDB runs them inside the database.
Tool use / agent loopthe model asks to call a tool, we run it, give back the result, repeat until it answers.
MCPModel Context Protocol: a standard way for an agent to discover and call tools served by a separate process.
SSEserver-sent events: how the server streams each step to the browser live.
git blamewho last changed each line; aggregated per function it gives ownership share.
Pull requesta proposed change on a branch that maintainers review and merge.
OpenAPI / Swaggera machine-readable description of an API: paths, methods, parameters, security.
Bundlethe compiled JavaScript a web app ships to browsers; it contains the API paths the frontend calls.
Driftroutes that exist only in the deployment or only in the analysed code revision.
