◉ Blast Radius

Graph-native security triage. FalkorDB Graph Hacks, Track 1: Agents That Act on Connected Data.
One sentence: Give it a vulnerability or a package, and the agent walks a FalkorDB graph of the codebase to tell you which HTTP endpoints can actually reach the vulnerable code, who owns that code, and then it fixes it: plans the version bump, verifies it with OSV, commits it on a branch, opens a pull request (or writes a report), and records the decision back on the graph.

1. The problem (what to say first)

Every dependency scanner produces a list. For mealie, a popular open-source recipe app, the v3.0.0 lockfile has 142 packages and 329 published advisories. Pillow alone has 36. A list is not a decision. The engineer on call needs three answers the list cannot give:

  1. Is it reachable? Does our code call the vulnerable library at all, or is it only installed?
  2. From where? Which HTTP endpoints can an attacker use to reach that code?
  3. Who fixes it, and to what version?
A scanner gives you a list. Triage is three graph questions: is it reachable, from where, and who owns it. So we made the graph the agent's brain.

The graph schema (memorise this line)

Vulnerability -AFFECTS-> Package <-USES- Function <-CALLS*- Function(handler) -EXPOSES-> Endpoint
Package -DEPENDS_ON-> Package          (transitive chain from poetry.lock)
Author -OWNS {lines, share}-> Function (git blame)   ·   Author -AUTHORED-> Commit -MODIFIED-> File
Vulnerability -TRIAGED-> Decision      (the agent writes its verdicts back: the graph is also its memory)

The one query that replaces an afternoon

MATCH (p:Package {name:'pillow'})<-[:USES]-(sink:Function)
MATCH path = (h:Function)-[:CALLS*0..4]->(sink)
MATCH (h)-[:EXPOSES]->(e:Endpoint)
RETURN e.id, sink.qualname, [n IN nodes(path) | n.qualname], length(path)

Answer in under 200 ms: 8 endpoints out of 248 can reach Pillow, all through PillowMinifier in 2 to 5 hops. The other 240 never touch it. That is the blast radius.

The agent loop

Claude runs a tool-use loop. It picks tools, we run the Cypher, it reads the rows, repeats. Method it follows: Identify → Reach → Owners → Fix → Act → Record. The model only sees tool results, so every endpoint, owner, and version in its answer comes from the graph. The UI shows the exact queries next to the answer.

ToolWhat it does
find_vulnerability, list_vulnerabilities, past_decisionsPin the advisory, installed version, fixed version. Check if it was triaged before.

5. Questions judges will ask

How is this different from Snyk or Dependabot?

They tell you a package is vulnerable. We tell you whether your code reaches it, through which endpoints, who owns it, and we open the fix. Reachability needs a call graph joined to the dependency graph joined to git history. That join is the graph.

Where is MCP in this?

Every tool lives in an MCP server (agent/mcp_server.py). The agent does not hard-code a tool list: it connects over MCP, asks the server what tools exist, and Claude selects among them. Judges can point Claude Desktop at the same server and triage from there. The envelope each tool returns carries the Cypher it ran and the subgraph it touched, which is how the UI stays explainable across the process boundary.

Why a graph database and not SQL or a vector store?

The core question is a variable-length path: endpoint to sink across an unknown number of calls. In Cypher that is [:CALLS*0..4]. In SQL it is a recursive CTE per question. A vector store cannot answer "is X reachable from Y" at all.

How accurate is the call graph?

Static Python resolution is imperfect, so every call edge records how it was resolved. The agent reports high confidence when every edge was resolved statically and medium when one was matched by method name. It also reads the sink's source before deciding. We also resolve FastAPI dependency injection, which is how auth reaches every protected route.

Does it hallucinate endpoints or owners?

The model only sees tool results, and the UI shows the queries. In our scenario tests every endpoint, owner and version in the answer appeared in a tool result.

What did FalkorDB specifically give you?

Variable-length paths in milliseconds, multi-graph so each analysed repo is its own graph, full-text indexes on code and advisory text, read-only query mode for the agent's escape hatch, and write-back of decisions so the graph is also memory.

Can it look at my running app, not just the code?

Yes. Paste the live URL in the header: it reads the OpenAPI document (following Swagger/Redoc pages), tries GraphQL introspection, scans the frontend bundles, and has Claude read the bundles' network-call code to extract endpoints assembled from constants and templates, then joins everything to the code graph. Endpoints become "confirmed deployed" with an auth flag, and routes that exist only in the deployment or only in the code are flagged as drift. On mealie's public demo: 271 live endpoints, 234 matched to code, 37 only deployed, 14 only in code. With your permission it can also send benign HEAD/GET/OPTIONS probes to confirm which endpoints answer without login.

Can it run on my repo?

Yes, live, four ways: a GitHub URL (private with a token), a zip upload, a local folder path, or just the app URL for a surface-only map. Paste a public GitHub URL in the header box: it clones, parses, pulls advisories from OSV, runs git blame and loads a new FalkorDB graph with a progress panel, usually in 2 to 20 seconds for a mid-size Python project. Supported today: Python (FastAPI, Flask, Django, Django REST Framework) and JavaScript/TypeScript (Express, Next.js, NestJS) with lockfiles; ORM models become Table nodes so it can name the data at risk. Not yet: unpinned dependencies, Java/Go. The parser is per-language; the graph schema and the agent are not.

What about running the tests after the bump?

Honest answer: not yet. The agent verifies the fix against OSV and commits it; CI runs the tests on the PR. A sandboxed test run is next.

6. Rules compliance (check before submitting)

  • FalkorDB is the primary database and does the real work: reachability, algorithms, ownership joins, decisions. Remove it and nothing runs.
  • Track named at submission: Agents That Act on Connected Data.
  • Data: public repos only, public OSV API, commit emails hashed (no personal data stored).
  • Public repository created, README has setup + graph data model, docs/queries.md lists every Cypher query and algorithm.
  • Demo video recorded and linked. Local setup instructions complete (make demo).
  • AI assistant use disclosed in README (Claude Code).
  • You can explain the graph model, the queries, the architecture and the decisions: work through docs/study-guide.md.
  • Main coding work inside Oct 15 to 18 (see the plan agreed with the assistant).
